Orator — App Map

A snapshot guide to how the code fits together. Generated at the end of the build; the code can drift past this commit.

What the app is

Orator is a debate sparring app. You pick a motion, a side, and an opponent level (Friendly, Strict, Hostile), argue in a chat, and a neutral judge analyzes every exchange: which rhetorical techniques each side used, who manipulated, and — after Stop or 10 exchanges — a final verdict. The opponent logs its own techniques as it argues, so the judge's statements about the opponent are ground truth, not guesses.

The main pieces:

  • public/ — the page: setup screen, debate stage, judge's column, verdict panel (index.html, app.js, styles.css). All state lives in the browser; nothing is saved.
  • server.js — Express server: three API routes, plus all validation of what the model returns.
  • src/prompts.js — the three role prompts (opponent, exchange judge, verdict) and their JSON shapes.
  • src/llm.js — the only file that talks to the model API (OpenRouter by default, GLM-5.3-flash), with JSON mode and one retry.
  • src/techniques.js — the fixed vocabulary of 20 rhetorical techniques; src/levels.js — the three opponent personas; src/topics.js — the eight motions.

Reference route through the code

This route was not toured interactively — use it as a reading order.

  1. public/app.js — find turnForm.addEventListener("submit", …): what the page sends and how the waiting/error states are handled.
  2. server.js — find app.post("/api/turn", …): opponent call, then sanitizeOpponentResult (quote checking, call-out routing), then the judge call with its own sanitizing.
  3. src/llm.js — find export async function callJson: the single place that knows the API endpoint, key, JSON mode, and retry rule.

To change this, start here

  • Opponent personality or toughness → src/levels.js (persona text and the allowed-technique lists per level).
  • Rhetorical techniques vocabulary → src/techniques.js; the prompts and validations pick the list up automatically.
  • Judge or verdict wording rules → src/prompts.js (judgeSystemPrompt, verdictSystemPrompt); length and consistency limits are enforced in server.js.
  • Topics and positions → src/topics.js.
  • Model provider or model id → no code change: edit .env (LLM_BASE_URL, LLM_API_KEY, LLM_MODEL); see .env.example.
  • Page look → public/styles.css; the layout skeleton is in public/index.html.

A practice to reuse

Make the model's claims checkable at the boundary. The opponent logs the techniques it used with exact quotes; server.js (sanitizeOpponentResult, quoteMatches) verifies every quote against the reply before the judge treats the log as ground truth — normalizing quotes, dashes, whitespace, and case first, dropping or re-routing entries that do not check out. The same idea works anywhere a model's output feeds downstream logic: define the verifiable fields, validate at one boundary, and decide explicitly what happens to a failed entry (retry, drop, or re-route) instead of letting bad data flow on.
